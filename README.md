# Перегон — геймифицированный тренажёр проводника ВСМ

Кейс «Геймификация для ВСМ», хакатон Московского транспорта.

Одна тренировка — один инцидент на перегоне Москва — Санкт-Петербург.
Проводник принимает решения на таймере, видит, как каждое из них двигает
**лояльность пассажира** и **рейтинг безопасности**, и после рейса получает
разбор: почему изменилась каждая шкала и как можно было лучше. Очки идут
в профиль компетенций, достижения и рейтинг бригад.

Сценарии построены не на выдумке, а на данных кейса: методичка
«Примеры ситуаций взаимодействия поездного персонала с пассажирами»
(51 ситуация) и стандарты СТО РЖД по обслуживанию пассажиров ВСМ.

## Что именно сделано

| Требование кейса | Где реализовано |
|---|---|
| Движок нелинейных сценариев с условиями | [`backend/app/engine.py`](backend/app/engine.py), сценарии — данные в [`content/scenarios/`](content/scenarios) |
| Таймеры на критические решения, истечение влияет на исход | ветка `timeout` у каждого узла с таймером; время считает сервер |
| Двойная шкала «лояльность» / «безопасность» | `Effects` в [`backend/app/domain.py`](backend/app/domain.py), итог — `engine.score` |
| Профиль, уровни, очки компетенций | [`backend/app/service.py`](backend/app/service.py), пять компетенций |
| Достижения | [`content/achievements.yaml`](content/achievements.yaml) + [`backend/app/achievements.py`](backend/app/achievements.py) |
| Таблица лидеров (бригада, депо, компания) | `service.leaderboard`, `GET /api/v1/leaderboard` |
| Обратная связь: разбор последствий каждого решения | `service.debrief`, экран «Разбор рейса» |
| Уведомления о сценариях, челленджах, сгорающих баллах | таблица `notifications`, `GET /api/v1/notifications` |
| Аналитика и пробелы в компетенциях | `service.hotspots`, `GET /api/v1/analytics/hotspots` |
| API для интеграции с HR/LMS | OpenAPI на `/docs`, описание — [`docs/02-api.md`](docs/02-api.md) |

## Три собственных решения, которых нет в «квизе с таймером»

1. **Ролевая модель как механика, а не как справка.** Методичка задаёт
   порядок: признать ситуацию → обозначить правило → предложить решение →
   заверить. Каждый вариант ответа помечен шагом этой модели, и движок
   считает **порядок** отдельно от самих реплик: правило, сказанное до
   признания, стоит −4 лояльности, решение после признания — +3.
   Правила лежат в `engine.SEQUENCE_RULES` — их видно и можно менять
   за минуту (см. [`docs/03-user-flow.md`](docs/03-user-flow.md)).
2. **Таймер от маршрута, а не от игры.** Часть действий возможна только до
   остановки: медиков вызывают к платформе, пассажира передают полиции на
   вокзале. Поэтому у сценария есть `minutes_to_stop`, а время решения
   считает **сервер** — в БД лежит момент показа узла, и клиент не может
   «остановить» таймер из консоли.
3. **Шкалы тянут в разные стороны осознанно.** Итог считается как
   `0.6 × безопасность + 0.4 × лояльность`: сервис не оплачивается риском,
   и это видно в баллах. При этом почти в каждом узле есть вариант,
   сохраняющий обе шкалы, — он отличается формулировкой, а не смыслом.

## Запуск

Нужен Python 3.11+ и ничего больше: база — SQLite, фронтенд без сборки.

```bash
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt   # Linux/macOS: .venv/bin/python
.venv/Scripts/python backend/seed.py                      # демо-данные: 5 проводников, рейтинг, уведомления
.venv/Scripts/python -m uvicorn app.main:app --app-dir backend --port 8040
```

- Интерфейс — <http://localhost:8040>
- OpenAPI/Swagger — <http://localhost:8040/docs>

Тесты:

```bash
.venv/Scripts/python -m pytest backend/tests -q
```

Контейнеризация: [`Dockerfile`](Dockerfile) собирает тот же стенд
(`docker build -t vsm-trainer . && docker run -p 8040:8040 vsm-trainer`).
На машине разработки Docker не установлен, поэтому образ не проверялся
запуском — локальный путь выше проверен и является основным.

## Структура

```
backend/app/domain.py    типы сценария: узлы, варианты, эффекты
backend/app/engine.py    ядро: ветвление, таймеры, шкалы, ролевая модель, итог
backend/app/loader.py    загрузка YAML + валидация ссылок между узлами
backend/app/db.py        схема SQLite
backend/app/service.py   партии, профиль, достижения, рейтинг, аналитика
backend/app/main.py      HTTP API (FastAPI) и раздача фронтенда
backend/seed.py          демо-данные: партии проигрываются тем же ядром
content/scenarios/*.yaml три сценария на данных кейса
content/achievements.yaml  восемь достижений с декларативными условиями
frontend/                интерфейс без сборки (HTML + CSS + JS, Moscow Sans)
docs/                    архитектура, API, user flow, ограничения и план
```

## Данные и безопасность

- Все профили, бригады и депо — **синтетические**, персональных данных
  пассажиров и сотрудников в стенде нет (152-ФЗ, ограничение кейса).
- Секретов и ключей в репозитории нет: конфигурации внешних систем не
  требуется, база создаётся локально при первом запуске.
- Некорректные обращения обрабатываются предсказуемо: неизвестный сценарий
  или партия — 404, недоступный вариант или повторный ход в завершённой
  партии — 409, битая ссылка между узлами сценария — ошибка **при загрузке**,
  а не в середине партии.
