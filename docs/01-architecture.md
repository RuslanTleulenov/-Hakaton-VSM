# Архитектура

Три слоя с жёсткой границей: ядро ничего не знает про HTTP и БД, прикладной
слой — про интерфейс, интерфейс — про содержимое сценариев. Поэтому сценарий
можно поменять, не трогая код, а хранилище — не трогая игровую логику.

```
┌──────────────────────────── браузер ────────────────────────────┐
│ frontend/  экраны: каталог → рейс → разбор, профиль, рейтинг,   │
│            аналитика, уведомления. Таймер только рисуется.       │
└───────────────────────────── REST ──────────────────────────────┘
                                │  /api/v1/*  (OpenAPI на /docs)
┌──────────────────────────── backend ────────────────────────────┐
│ main.py     HTTP: валидация запросов, коды ошибок, раздача SPA, │
│             интеграции с HR/LMS по токену X-API-Key             │
│ service.py  партии и рейсы, профиль, достижения, рейтинг,       │
│             челлендж, серии, аналитика; время по часам сервера  │
│ engine.py   ЯДРО: ветвление, таймеры, шкалы, ролевая модель,    │
│             память рейса, альтернативы, итог — детерминированно │
│ domain.py   типы сценария и рейса   loader.py  YAML + валидация  │
│ db.py       SQLite: conductors, runs, run_events,               │
│             earned_achievements, notifications, api_clients      │
└─────────────────────────────────────────────────────────────────┘
                                │
            content/scenarios/*.yaml · content/trips/*.yaml · achievements.yaml
```

## Последовательность одного хода

```
браузер                 main.py            service.py           engine.py         SQLite
   │ POST /runs            │                   │                    │                │
   │──────────────────────>│──────────────────>│ start_run          │                │
   │                       │                   │ engine.start ─────>│                │
   │                       │                   │ INSERT runs (state, node_shown_at) ─>│
   │<─ узел + таймер ──────│<──────────────────│                    │                │
   │ POST /runs/{id}/choose│                   │                    │                │
   │──────────────────────>│──────────────────>│ seconds = now − node_shown_at       │
   │                       │                   │ engine.choose ────>│ эффекты, шаги, │
   │                       │                   │                    │ таймаут, финал │
   │                       │                   │ INSERT run_events, UPDATE runs ─────>│
   │<─ шкалы, причины ─────│<──────────────────│ если финал: score, ачивки, XP       │
```

Ключевое: `seconds` считает сервер. Клиент не передаёт время вообще —
он может только не прислать ход (`option_id: null`), и тогда ядро само решит,
истёк ли таймер.

## Рейс из нескольких инцидентов

Обычная партия — один инцидент. Рейс — очередь инцидентов с общим состоянием:

```
RunState.queue = ["lost-child", "medical"]      # что осталось в смене
RunState.flags = {"goodwill_car", "chief_informed"}   # память пассажиров
RunState.loyalty / safety                        # шкалы не обнуляются
```

Когда инцидент доходит до финального узла, а очередь не пуста,
`engine.continue_trip` переводит партию к следующему сценарию, сохраняя
шкалы, компетенции и флаги, и записывает исход в `segments`. Память работает
двумя способами: `requires` / `forbidden` открывают и закрывают варианты,
`goto_if` уводит тот же ход в другой узел. Расшифровка флагов для игрока
лежит в рейсе (`memory_labels`) — ядро именами флагов не интересуется.

## Почему так

- **Ядро без БД и HTTP.** Партия воспроизводится в тесте одной функцией:
  `engine.choose(scenario, state, "radio", seconds=5)`. Одиннадцать тестов
  прогоняют реальные линии сценариев — именно поэтому таблица лидеров честна.
- **Сценарий — данные.** Методист добавляет ситуацию из методички, не трогая
  Python. Ссылки между узлами и неизвестные компетенции ловятся **при
  загрузке**: битый сценарий не доживает до партии.
- **SQLite.** Жюри запускает стенд одной командой без установки СУБД.
  Слой узкий (`db.py` + запросы в `service.py`) — переезд на PostgreSQL
  меняет только его.
- **Фронтенд без сборки.** Нет node_modules и шага компиляции — меньше
  способов сломать запуск по инструкции. Разделение с бэкендом сохранено:
  общение только через REST, фронтенд можно вынести на любой статик-хостинг.

## Масштабирование

Состояние партии лежит в БД, а не в памяти процесса, поэтому бэкенд
горизонтально масштабируется за балансировщиком без липких сессий.
Узкое место при росте — SQLite; замена на PostgreSQL затрагивает `db.py`
и несколько запросов с `json_extract`.

## Интеграция с внешними системами

Игровые методы и интеграционные разделены: внешние системы ходят в
`/api/v1/integration/*` с заголовком `X-API-Key`, который проверяется
зависимостью `integration_client` по таблице `api_clients`.

- Выгрузка прогресса в HR/LMS: `GET /api/v1/integration/progress`
  (учебные показатели без ФИО — принцип минимизации данных).
- Назначение обучения из LMS: `POST /api/v1/integration/assign` —
  проводник получает уведомление в приложении.
- Аналитика для методистов: `GET /api/v1/analytics/hotspots` и `/trend`.
- Схема OpenAPI отдаётся машинно: `/openapi.json`.
