# Ограничения решения и план развития

## Что сознательно не сделано

| Ограничение | Почему |
|---|---|
| Аутентификации проводников нет: вход по логину без пароля | демо-стенд; в контуре ВСМ вход идёт через корпоративный SSO, а профиль приходит из HR-системы. Имитировать это паролями в открытом стенде хуже, чем не делать вовсе. Интеграционный контур при этом уже закрыт токеном |
| SQLite вместо серверной СУБД | запуск жюри одной командой важнее нагрузочных характеристик; слой хранилища изолирован (`db.py` + запросы в `service.py`) и меняется без правки игровой логики |
| Шесть сценариев, а не все 51 из методички | ценность в глубине ветвления, а не в числе линейных ситуаций: 53 узла, 92 варианта, условия и память. Формат позволяет добавлять остальные без кода |
| Редактор сценариев — не веб-интерфейс, а YAML плюс валидатор | `python backend/validate.py` ловит битые ссылки, недостижимые узлы, варианты без причины и «пустые» варианты. Визуальный редактор — следующий шаг, формат под него готов |
| Фронтенд без сборки, не PWA | надёжный запуск по инструкции важнее офлайн-режима; вёрстка адаптивная и играется с телефона, но установки на устройство нет |
| Образ Docker не проверялся запуском | на машине разработки Docker не установлен; `Dockerfile` и `docker-compose.yml` написаны, но основной проверенный путь — локальный запуск из README |
| Разбор ссылается на документ, а не на конкретный пункт | методичка и СТО РЖД из датасета цитируются на уровне ситуации («ситуация 19»); пунктовая привязка требует сверки с актуальной редакцией стандарта |
| Эффекты решений расставлены экспертно | веса выведены из методички и здравого смысла, а не из статистики обращений: её у нас нет. Калибровка — в плане развития |
| Уведомления живут внутри приложения | push и почта требуют внешних сервисов, которых в демо-контуре нет; механизм и API готовы, нужен только транспорт |

## План развития

**Ближайшее (недели)**

1. Веб-редактор сценариев для методистов: тот же YAML, визуальный граф узлов,
   проверка связности при сохранении, предпросмотр партии.
2. Остальные ситуации методички, приоритет — по данным `hotspots`:
   сначала темы, где проводники ошибаются чаще всего.
3. Рейсы под класс обслуживания и время суток; ночная смена с усталостью
   как отдельным ресурсом.
4. Уведомления наружу (push, почта) и еженедельные командные челленджи
   между бригадами.

**Средняя перспектива**

5. SSO и профиль из HR, назначение обучения из LMS по расписанию,
   выгрузка результатов в учётную систему подготовки.
6. Роль инструктора: назначить рейс бригаде, посмотреть разбор конкретной
   партии, оставить комментарий к ходу, собрать группу на разбор ошибок.
7. Свободная реплика вместо выбора варианта: ответ проводника распознаётся
   в один из ходов, а исход по-прежнему считает детерминированное ядро —
   так модель не может «сломать» оценку, а офлайн-режим сохраняется.

**Дальше**

8. Голосовой режим: интонация и темп речи как часть оценки.
9. Мультиплеер «проводник — начальник поезда» на одном инциденте.
10. Калибровка весов по реальной статистике обращений пассажиров и
    инцидентов: тогда балл тренажёра можно будет сопоставлять с практикой.
